= Configure MetroCluster IP interconnect congestion control

:icons: font
:imagesdir: ../media/


[.lead]
Beginning with ONTAP 9.20.1, you can enable congestion control in MetroCluster IP configurations so that Inter-Switch Links (ISLs) running at lower or mixed bandwidths, such as 10Gbps, 25Gbps, or 40Gbps, can be used with platforms that have a MetroCluster IP backend port speed of 100Gbps.

Replication traffic generated by the 100Gbps adapter can overrun ISLs with a lower link speed, causing switch buffer pressure, PAUSE backpressure, packet loss, and potential replication instability. MetroCluster IP interconnect congestion control adaptively throttles replication traffic when ONTAP detects that the ISL bandwidth is insufficient to absorb outbound throughput.

== About this task

* The MetroCluster IP configuration must be running ONTAP 9.20.1 or later.
* Congestion control is disabled by default and must be explicitly enabled by the storage administrator on both clusters in the MetroCluster IP configuration. It can be enabled or disabled at any time after you set up the MetroCluster clusters.
* If ISL speeds are uniformly 100Gbps, enabling this feature has no operational effect; throttling is only triggered when backpressure signals are detected.
* Congestion control operates automatically after it is enabled. 

== Enable MetroCluster interconnect congestion control

.Steps

. Enable congestion control on cluster_A:
+
[source,cli]
metrocluster interconnect congestion-control enable

. Verify that congestion control is enabled:
+
[source,cli]
metrocluster interconnect congestion-control show
+
----
cluster_A::> metrocluster interconnect congestion-control show

Status: enabled
T_auto (MiB/s): 2400
cur_wafl_thrpt (MiB/s): 3100
num_rejected_reqs: 142
suspend_msecs: 12
Driving-signal summary: rx_pause
----
+
NOTE: The output should show that the status is `enabled`.

. Repeat the previous steps on the partner cluster.

== Disable MetroCluster interconnect congestion control

.Steps

. Disable congestion control on cluster_B:
+
[source,cli]
metrocluster interconnect congestion-control disable


. Verify that the feature is disabled:
+
[source,cli]
metrocluster interconnect congestion-control show
+
The output should show the status as `disabled`.

. Repeat the steps on the partner cluster.

== Monitor congestion control activity

You can use the following command to monitor active throttling behavior and verify that congestion control is functioning as expected:

[source,cli]
metrocluster interconnect congestion-control show

When enabled, the output should be similar to the following example:

----
cluster_A::> metrocluster interconnect congestion-control show

Status: enabled
T_auto (MiB/s): 2400
cur_wafl_thrpt (MiB/s): 3100
num_rejected_reqs: 142
suspend_msecs: 12
Driving-signal summary: rx_pause
----


=== Output field descriptions

[cols="2,4",options="header"]
|===
| Field | Description

| `status`
| Indicates whether congestion control is `enabled` or `disabled`.

| `T_auto`
| The current auto-derived throughput threshold (MiB/s). ONTAP calculates this value dynamically based on observed ISL capacity.

| `cur_wafl_thrpt`
| The live measured replication throughput (MiB/s).

| `num_rejected_reqs`
| The number of replication requests that have been throttled since the last reset. A non-zero value indicates active throttling.

| `suspend_msecs`
| The duration (in milliseconds) of the most recent throttling window.

| `Driving-signal summary`
| The primary backpressure signal currently driving throttling decisions. Common values include `rx_pause` (indicating received PAUSE frames from the switch) and `tx_queue_overflows` (indicating transmit queue saturation on the local adapter).
|===


== Troubleshooting

[cols="3,4",options="header"]
|===
| Symptom | Recommended action

| High `num_rejected_reqs` with sustained `rx_pause` signal
| Verify switch ISL port speeds and confirm that switch buffer allocations are appropriately configured for the speed mismatch.

| Feature enabled but `num_rejected_reqs` remains 0
| ISL speeds are likely sufficient. No action required; throttling only activates under backpressure conditions.

| Replication latency persists after enabling congestion control
| Check for additional causes such as ISL packet loss, switch port errors, or SFP compatibility issues. Review switch port statistics independently.
|===
